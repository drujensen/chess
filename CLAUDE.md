# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A terminal chess app written in Crystal. The human picks white, black, or random at the start of a new game (`Chess#select_side`); whichever side isn't human is played by a local Ollama model (`qwen3.8:latest`, currently) via its OpenAI-compatible chat completions endpoint, using function/tool calling. The human can enter moves in long algebraic notation (e.g. `e2e4`) or as natural language (e.g. "move my king pawn up two squares"), which the model resolves against the actual legal moves for whichever side the human is playing. The board is rendered with unicode chess characters and ANSI background colors, flipped to black's perspective (rank 1 at top, files h->a) when the human is playing black.

## Commands

- Build: `shards build` (produces `./bin/chess`)
- Run: `./bin/chess`, or `crystal run src/chess.cr` during development
- Run all specs: `crystal spec`
- Run a single spec file: `crystal spec spec/pieces/pawn_spec.cr`
- Run a single example: `crystal spec spec/pieces/pawn_spec.cr -e "allows white pawn to move forward one square"`

Requires a local Ollama server by default, with a tool-calling-capable model pulled (`qwen3.8:latest`, currently). The endpoint, model, and per-request timeout are configurable via `CHESS_BASE_URL`/`CHESS_MODEL`/`CHESS_TIMEOUT` env vars (see `src/ai.cr`'s `BASE_URL`/`MODEL`/`TIMEOUT` constants - `TIMEOUT` defaults to 300s), so pointing them at the real OpenAI API (and setting `CHESS_API_KEY`) works too. `CHESS_PROVIDER` (e.g. `xai`, `deepseek`, `openai`, `drujensen`) is a shortcut for that: it looks up a base URL and that provider's own API key env var (e.g. `XAI_API_KEY`, or `OPENAI_API_KEY` for the `openai` entry) from `AI::PROVIDERS`, so switching providers already exported in a `.profile` is one env var instead of re-exporting `CHESS_BASE_URL`/`CHESS_API_KEY` each time; `CHESS_BASE_URL`/`CHESS_API_KEY` still override it directly when set. `Chess#initialize` prints the resolved model and base URL at startup so it's never ambiguous which provider is actually active.

Post-game analysis (`Analysis`, below) and live hints (`Hint`, below) both need a `stockfish` binary on `PATH` - optional in each case, degrading to a one-line notice when absent, and the specs that call the real engine (`spec/analysis_spec.cr`, `spec/hint_spec.cr`, both tagged `"stockfish"`) self-skip via `pending!` when it's missing. Hint strength is tunable via `CHESS_HINT_DEPTH` (see `src/hint.cr`, defaults to 16); the top-5 count is deliberately hardcoded.

## Architecture

- `drain_stdin` (top-level function in `src/chess.cr`, not a `Chess` method - callable from both the module-level menu loop and inside `Chess`) - sets `STDIN.read_timeout` to 50ms and reads until it times out or hits EOF, discarding whatever it reads, then resets `read_timeout` back to `nil` (leaving it set would give *every* later blocking `gets` call the same 50ms timeout and raise `IO::TimeoutError` on real, valid waits). Called right before every prompt-reading `gets` (skill-level selection, white's move, the main menu, the overwrite-confirmation). Fixes a real bug: without it, a stray keystroke typed while the AI was "thinking" sits in the OS input buffer and gets consumed by whichever `gets` call happens next - not the prompt that was on screen when it was typed - so e.g. quitting at the post-game menu could silently turn into "start a new game" because an earlier keypress was still queued up.
- `src/chess.cr` - entry point. The top-level loop is a menu (new game / resume game / browse saved games / quit) dispatching to `Chess.new.run`, `Chess.new(SavedGame.load).run`, or `Replay.browse`; choosing "new game" while a `SavedGame` exists asks for confirmation before it gets overwritten. `Chess` is the game loop itself. `@white` tracks whose turn it actually is; `@human_white` (set once, at game start) tracks which color the human is playing - the two are deliberately separate, since the human can now be either color, so every "is it the human's turn" check in `next_turn` is `@white == @human_white`, not a bare `@white`. New games call `select_side` (White/Black/Random, the latter a coin flip resolved once and then fixed for the rest of the game) right after `SkillLevel.prompt`; resuming instead reads the already-resolved `saved.human_white` (defaulting to `true` for saves written before this existed, which were always human-as-white). Loads the human's `Profile` and, when resuming, replays the saved moves onto a fresh `Board` and re-briefs a fresh `AI` with the game-so-far via `resume_moves` - the model's exact prior conversation can't survive a restart, only the position and move list. `AI.new`'s `ai_white` param (`!@human_white`) is what tells the model which color it's actually playing - see `src/ai.cr`. `@board.draw(!@human_white)` flips the board to black's perspective whenever the human is playing black. Typing `hint` on the human's turn shows the engine's top five moves for the human's own color instead of playing anything - `Chess#show_hint` (see `src/hint.cr`), matched as an exact, case-insensitive word alongside the `undo`/`resign`/`quit` handling and `return`ing before any move is parsed. It plays nothing, so it deliberately skips *all* the bookkeeping a real move does: no `@error_count`/`@last_error` reset, no `save_progress` (the board is unchanged, and an earlier app-level check confirmed typing `hint` then `quit` leaves no `~/.chess/in_progress.json` behind), and above all nothing is pushed into the AI's `@messages` - the model's account of the game only ever covers what actually happened on the board, so a hint the human may have just ignored must not become a fact the model believes. It's also color-correct by construction: it hints for `@human_white`, not for a hardcoded side, so it works the same when the human plays black. Typing `quit`/`exit`/`save` on the human's turn (or stdin EOF) just raises a plain message ending `run` - no special handling needed to avoid losing progress, because `save_progress` (below) already persists after every move. Typing `resign` (human) or the model calling the `resign` tool (AI, see `src/ai.cr`) instead raises a `GameOver` with a result/message built from whichever color actually resigned - a real result, not just a pause, so it flows through `finish_game` the same as checkmate/stalemate/draws. The human's `resign` is gated on `Board#only_pawns_left?(@human_white)` first, same as the AI's own `resign` tool - a prompt-only version of this bar (see `src/ai.cr`) still let a model resign right at the edge of whatever threshold the wording set, so the rule is also enforced here as a plain board fact instead: no piece other than pawns (and the king) left, full stop, applied identically to both colors. Rejected, it just prints why and `return`s instead of raising, leaving the human free to `quit` (a pause, not a loss) if they really want out. The human's `gets` returning `nil` (stdin EOF) raises immediately rather than looping - `gets` never blocks again once stdin is closed, so treating it as "no more input" is what stops that from becoming a busy loop; blank input is silently ignored (re-prompts) without spending an AI call on it. The human's non-notation input is first sent to `AI#resolve_move(board, move, @human_white)`, which tries to resolve it to one of the position's actual legal moves for whichever color the human is playing; on success the exchange is recorded into the AI's shared history via `AI#record_move_resolution` (so later chat/moves have it in context, not just the bare notation `board.moves` shows) and the move is played; if that fails (not a move, ambiguous, illegal), it falls back to `AI#chat` so the human can "talk" to the AI mid-game - `AI#chat` itself is told explicitly, every time, that this already failed move resolution (see `src/ai.cr`), since the model otherwise has no way to know that and - on a near-miss typo - has been observed to free-text echo the same `"(played X)"` phrasing real resolved moves get recorded with, falsely implying a move was played when nothing actually touched the board. A failed `board.turn` sets `@last_error` to `"invalid move: X - #{board.explain_invalid_move(move, white)}. try again!"` - a concrete reason (off the board, not your piece, square occupied by your own piece, that piece can't move that way, or leaves your own king in check), not just a bare rejection - threaded into the *next* `AI#next_move` call so the model actually sees why its last attempt failed (this is a plain instance var precisely so it survives across `next_turn` calls for the same side's turn, unlike a method-local variable). ...`Chess#save_progress` writes the move list (plus `human_white`) out to `SavedGame` (`~/.chess/in_progress.json`) after *every* successful move, not just on a clean exit. After every successful `Board#turn`, `Chess#report_game_status` checks the side to move next for checkmate/stalemate, the fifty-move rule, or threefold repetition - each raises a `GameOver` (carrying a PGN result code from white's perspective, e.g. `"1-0"`) caught by `run`'s typed `rescue ex : GameOver`, which calls `Chess#finish_game` to clear the now-obsolete `SavedGame`, translate that white-relative result into a score *for the human* (`@human_white == (result == "1-0") ? 1.0 : 0.0`, since the human may be either color) before calling `Profile#record_result` against the AI's `SkillLevel#elo_midpoint` as the opponent rating, and write the game out via `Board#to_pgn` with the `White`/`Black` PGN headers assigned according to `@human_white` rather than assuming the human is always White. A plain invalid-move abort (`error_count > 3`) raises an untyped exception instead, falling through to the generic `rescue ex` so it does *not* touch the profile, write a PGN, or clear the in-progress save. Check (not mate) just prints a warning. Typing `undo` (optionally `undo N`) on the human's turn, or the AI calling its own `undo` tool mid-`chat` (caught as an `UndoRequested`, see `src/undo_requested.cr` and `src/ai.cr`), both land on `Chess#undo(rounds)` - the one place that knows how to roll the game back. It always removes an *even* number of plies (one full round per unit of `rounds`: the human's move and the AI's reply to it), clamped to however many moves actually exist, specifically so the human always lands back on their own turn to move - an odd-ply undo would hand the very next turn straight to `ai.next_move` with no chance to undo further or play something else, defeating the point of "undo multiple times." There's no inverse of `Board#turn` (too much side state - captures, castling rights, en passant, repetition counts - to safely unwind by hand), so `undo` rebuilds a fresh `Board` and replays whatever's left, exactly like resuming a saved game does; it likewise replaces `@ai` with a fresh `AI` briefed via `resume_moves` on the rolled-back position, rather than trying to surgically trim the old one's `@messages` - which would be especially fragile when the rollback was *triggered* by an unanswered tool call from the AI's own `undo` tool (see the dangling-tool_call bug this app already hit once with DeepSeek). `undo` also resets `@error_count`/`@last_error` and calls `save_progress` immediately, so Ctrl+C right after an undo doesn't lose it. The AI's `setup_position` tool (also chat-only, see `src/ai.cr`) works the same way for jumping straight to an arbitrary position - e.g. "show me the Ruy Lopez" - caught as a `SetupRequested` (see `src/setup_requested.cr`) and landed on `Chess#setup_position(moves)`, which rebuilds from scratch exactly like `undo` does, except it doesn't try to land back on the human's turn - whichever side moves next from the requested position just moves next. The AI's `play_for_human` tool (chat-only too, see `src/ai.cr`) lets the human hand their own turn to the AI - e.g. "move for me" - caught as a `MoveRequested` (see `src/move_requested.cr`) in the same `begin`/`rescue` around `ai.chat` that catches `UndoRequested`/`SetupRequested`, except it doesn't return afterward: it falls through into the same `"playing X for you."` + `record_move_resolution` + `board.turn` path that an already-resolved natural-language move (`AI#resolve_move`) uses, since both are ultimately "a human-turn move the human didn't type directly" and should be applied and reported on identically.
- `src/board.cr` - `Board` holds the 8x8 `pieces` grid (`Array(Array(ChessMan))`, indexed `[y][x]`), captured-piece lists, the long-algebraic move history (`moves`, formatted like `"w: e2e4"`), and the SAN move list (`sans`, e.g. `"Qxh4#"`) built for PGN export. `Board#turn` is the single chokepoint for all move legality and side effects: notation parsing, bounds/ownership checks, delegating to the piece's `valid?`, rejecting moves that leave the mover's own king in check (`move_leaves_king_in_check?`, via a simulate-then-revert on the piece grid), computing the move's SAN prefix (`san_prefix_for`, which must run before the board mutates - it needs the pre-move piece identity, capture, and disambiguation), then applying castling, pawn promotion (auto-queen), en passant setup/capture (flags expire after the single following move - the capture side of this is only applied when the mover was a pawn *and* the destination square was empty before the move, i.e. `was_pawn_move && lost.is_a?(Empty)`; without that guard, an ordinary diagonal pawn capture onto an occupied square would additionally, wrongly, delete whatever piece happened to sit on the "captured en passant" square, since the rank/file arithmetic alone can't tell a real en passant from a normal capture), updating captured lists, the fifty-move clock, position-repetition count, and finally the SAN's check/mate suffix (needs the post-move position, so it's the last thing computed). `Board#legal_moves(white)` enumerates every fully-legal destination for a color (reused for check/checkmate/stalemate detection, skill-level blunder injection, SAN disambiguation, and grounding the natural-language move resolver). `Board#to_fen(white_to_move)` renders the position as FEN for the AI's `board` tool, built on the same `position_key` (piece placement + side to move + castling rights + en passant target, without the move counters) used to detect `draw_by_repetition?` in `position_counts`; `draw_by_fifty_move_rule?` just checks `halfmove_clock >= 100`. `Board#to_pgn(headers, result)` renders `sans` as a standard PGN move list with header tags, ending in a blank line (not just a newline) per the PGN spec's game separator - each of our saved games is its own file, but external multi-game database tools (e.g. PyChess) build their game list from `[Event]` tags and need that blank line to also find where each game's movetext ends, or they'll list a game but show it blank when opened; `Board#find_move_for_san(san, white)` is the inverse - given a SAN token, finds which of `legal_moves` produces it, used by `Replay` to step through a saved game. `Board#move_to_san(move, white)` is a third variant, for a candidate move that was never actually played (e.g. an engine's suggestion in `Analysis`) - it can't include a check/mate suffix, since that needs the position after playing the move. `Board#explain_invalid_move(move, white)` retraces `#turn`'s own checks in the same order and returns which one a rejected move actually failed - only meaningful to call after `#turn` already returned `false`. `Board#draw(flipped = false)` prints the board with per-square ANSI background codes computed from `(x + y).even?` (light/dark) rather than hardcoded per cell, so `flipped` (rank 1 at top, files h->a) is just reversing the rank/file iteration order rather than a second hand-written rendering path (not to be confused with the draw-detection methods above). `#turn` records the squares it just moved between as `last_move_from`/`last_move_to` (`Spot?`, `nil` until a move has actually been played) right before it returns `true`; `#draw` swaps in `LIGHT_SQUARE_HIGHLIGHT`/`DARK_SQUARE_HIGHLIGHT` (muted gold-tinted variants of the plain gray `LIGHT_SQUARE`/`DARK_SQUARE`, a step up in contrast rather than an unrelated color) for whichever two squares match, so the last move played is easy to spot at a glance. Needed no new plumbing anywhere else: `undo`/`setup_position` (`Chess`) and `Replay#step` all already rebuild a fresh `Board` and replay moves one at a time via `#turn` to reach whatever position they're showing, so the last `#turn` call in that replay is automatically the one highlighted - exactly the move each of those screens is actually about. `Board#only_pawns_left?(white)` is true once that color has nothing left but pawns (and its king) - a hard, board-level fact rather than an opinion, used to gate resignation for both the AI's `resign` tool and the human's typed `resign` (see `src/ai.cr`/`src/chess.cr`) after a model resigned twice while still holding a genuine piece.
- `src/pieces/` - one class per piece type, all subclassing `ChessMan` (`src/pieces/chessman.cr`), which is abstract and declares `valid?(board, from_x, from_y, to_x, to_y)`. Each piece's `valid?` computes candidate destination `Spot`s given the current board state and checks membership; pieces do not mutate board state themselves and don't consider check/pins - that's `Board`'s job. `Empty` is a null-object placeholder for empty squares, also a `ChessMan`.
- `src/spot.cr` - simple `Comparable` `(x, y)` coordinate value type used when generating candidate moves.
- `src/skill_level.cr` - `SkillLevel` enum (Novice through Grandmaster) with an Elo range and a `weak_move_chance` per tier. `AI#next_move` rolls against it each turn and, if it hits, adds a system message explicitly telling the model to play like that tier *before* it chooses - the model's own account of the game always matches the move it actually submits; there is no post-hoc substitution (an earlier version silently swapped in a random legal move after the model chose, which desynced the model's belief about the position from the real board - it would report having played one move while a different one appeared on the board). That roll also decides whether the engine's ranking reaches the model at all: when it fires, `next_move` withholds the `hint` notice (see `AI#turn_notices`) so a Novice can't lean on a 3000-strength answer and defeat the point of the tier. The hint is *attached to the request* rather than offered as a tool the model has to choose to call - DeepSeek was given a `hint` tool on every move of a real game and used it zero times, so opt-in was a no-op; prompt wording alone has repeatedly proven unreliable here (same lesson as the `resign` gate). Master/Grandmaster never get the nudge - their real strength is whatever the underlying model can play, plus the engine ranking it's handed every turn. `elo_midpoint` gives a representative Elo per tier, used as the "opponent rating" for the human's Elo update. `.prompt` renders the numbered menu and parses the answer (defaulting to Advanced), shared verbatim by `Chess.new` (a brand new game) and `Replay#start_new_game_from_here` (jumping from a replayed position into live play) - both need a skill level chosen the same way, and a finished game's PGN has nowhere to recover its original one from anyway.
- `src/profile.cr` - `Profile` is the human player's persistent record (name, `rating`, win/loss/draw counts), serialized via `JSON::Serializable` to `~/.chess/profile.json` (`Profile.load`/`#save`). `#record_result(opponent_rating, score)` applies the standard Elo formula (K=32).
- `src/game_over.cr` - `GameOver < Exception` carries a PGN result code (`"1-0"`/`"0-1"`/`"1/2-1/2"`) alongside its message, so `Chess#run` can tell a real chess ending apart from any other exception.
- `src/undo_requested.cr` - `UndoRequested < Exception` carries a `count` (how many of the human's own moves to roll back), raised from `AI#chat_loop` when the AI calls its own `undo` tool and caught by `Chess#next_turn`, same shape as `GameOver` above.
- `src/setup_requested.cr` - `SetupRequested < Exception` carries the already-validated `moves` sequence from the AI's `setup_position` tool, same shape as `UndoRequested` above.
- `src/move_requested.cr` - `MoveRequested < Exception` carries a single already-validated long-algebraic `move` from the AI's `play_for_human` tool (the human asking the AI to play their own turn for them, e.g. "move for me"), same shape as `UndoRequested`/`SetupRequested` above - except `Chess#next_turn` doesn't rebuild anything for it, it just applies `move` the same way any other human-turn move gets applied.
- `src/game_log.cr` - `GameLog` appends to `~/.chess/chess.log` (`.info`/`.error`, the latter optionally taking the actual `Exception` to append its class/message/backtrace) instead of printing - keeps the terminal showing only what the player actually cares about (moves, prompts, results) while tool-call chatter (every `moves`/`board`/`move`/`undo`/`setup_position`/`play_for_human`/`hint` call, the `next_move` tool list offered on each turn, and a model replying without a tool call at all - see `src/ai.cr`) and background failures (a retried HTTP request's intermediate failures, or the backtrace behind whatever one-line message `Chess#run`'s generic `rescue ex` or `Replay#explain`'s `rescue` already shows the player) still end up somewhere inspectable on disk instead of vanishing.
- `src/saved_game.cr` - `SavedGame` is the one in-progress-game slot (only one at a time), serialized to `~/.chess/in_progress.json`: the plain-notation move list, the chosen `SkillLevel` (by name), which color the human is playing (`human_white`, defaulting to `true` so a save from before this field existed - always human-as-white - still loads correctly), and a timestamp. `Chess` writes it after every move and clears it when a game actually ends, so it only ever exists while a game is genuinely mid-play.
- `src/replay.cr` - `Replay` (a module of class methods, no state of its own) lists PGN files under `~/.chess/games`, parses each one's header tags and move list via `Analysis.parse` (which returns SAN plus any embedded NAG/comment, working equally on plain and already-analyzed PGN), and resolves the SAN tokens back to long-algebraic moves one at a time via `Board#find_move_for_san(san, white)` - which just searches `legal_moves` for the candidate whose `san_prefix_for` output matches, avoiding a separate SAN parser. If the game isn't yet annotated (`Analysis.annotated?`) and Stockfish is available, `#maybe_analyze` offers to run it (`Analysis.analyze`, showing progress) and rewrites the file in place via `Analysis.embed` so this only ever runs once per game; if Stockfish isn't installed, it prints a one-line warning and replay continues unannotated. `#step` then lets the user move through the resolved move list (`n`/`p`/`j <n>`/`q`), rebuilding a fresh `Board` from `setup` up to the current index on every step rather than supporting true undo, printing the current move's eval (always, once analyzed) and its label/better-move (when flagged) above the board, plus the long-algebraic move played next to the `move N/M` counter - the board itself stays exactly where it was, unaffected. On a flagged move, an `[e]xplain` option appears; `#explain` shows the cached `Note#explanation` if one exists, or computes one by pairing a fresh single-position `Stockfish` lookup (for the principal variation on both sides - the concrete "what actually happens" evidence) with `AI#explain_move` (which only narrates that evidence, never calculates anything itself - seconds-long lookups are fine here since it's one on-demand call, not a whole game), then persists it back into the same file via `Analysis.with_explanation` + `Analysis.embed` so it's never recomputed. `#explain` is called from a `begin/rescue` in `#step`, not left to propagate - an `AI#explain_move` timeout (or any other error) would otherwise climb all the way past `Replay`/`Chess` to the top-level menu `loop`, which has no rescue of its own and would crash the whole program instead of just failing this one lookup. `#step`'s `[s]tart new game from here` option (`#start_new_game_from_here`) lets the human jump out of replay and back into live play from whichever position is currently on screen - e.g. to try something different at a spot that now looks like a mistake. It reuses the exact resume path a `SavedGame` already takes rather than inventing a separate one: it builds a `SavedGame` directly from `moves[0...index]` plus a freshly-prompted `SkillLevel` (`SkillLevel.prompt` - PGN headers don't record the original opponent's skill level, so this can't be recovered, only re-asked) and `human_white` (recovered by matching `headers["White"]?` against `Profile.load.name`, since White/Black in a finished PGN is always the human's `profile.name` on one side and the AI's own `"AI (tier, ~elo)"` string on the other - see `Chess#finish_game` - never two humans, so this match is reliable), then hands it to `Chess.new(saved).run` exactly like resuming an in-progress game does. Same overwrite confirmation as the top-level menu's "new game" option if a `SavedGame` already exists, since this also replaces that one in-progress slot. Returns `false` without starting anything if the human backs out of that confirmation, so `#step` knows to keep replaying rather than stop; a `true` return (a game was actually started, and has now ended) instead breaks `#step`'s loop - there's no reason to keep stepping through the old finished game once the human has played a whole new one from partway through it.
- `src/stockfish.cr` - `Stockfish` is a thin UCI (Universal Chess Interface) client for a local `stockfish` subprocess, used by `Analysis` (post-game) and `Hint` (live). `.available?` checks `Process.find_executable("stockfish")` rather than assuming; `#evaluate(fen)` sends `position fen ...` + `go depth N` over the process's stdin and parses `info ... score cp|mate N ... pv ...` / `bestmove` lines off stdout, returning the side-to-move's score, suggested move, and principal variation (the forced-ish continuation, in long algebraic notation - kept for `Replay#explain` to hand the AI as concrete evidence, not asked of it). One process is kept open and reused across the whole game's positions during `Analysis.analyze`, not respawned per move; `Replay#explain` and `Hint` each spin up a separate short-lived one for their own one-off lookups. `#top_moves(fen)` is the multi-line variant, used by `Hint` to get a *ranked list* rather than just the winner: constructing with `multipv > 1` sends `setoption name MultiPV value N`, which makes the engine emit one `info depth X multipv K ...` line per candidate per depth, so `top_moves` keys each lane `K` separately (last write per lane wins = its deepest value), sorts by lane, and returns up to N `{cp, mate, move, pv}` tuples best-first. It ignores `info string` noise and `lowerbound`/`upperbound` lines (a lane's provisional score mid-search, not a final ranking), and requires both a score and a pv on the same line before recording a lane. Scores are from the side to move's perspective, exactly as UCI reports them, so no sign-flipping is needed by callers. A `move` from a lane is the pv's first move in the engine's own UCI spelling - so a promotion comes back as `e7e8q`, *longer* than the 4-char form the rest of the app uses (see `Hint.normalize_move`). Both readers share one private `search(fen, &block)` loop. **Real crash to know about:** this build of Stockfish is assertion-enabled and aborts outright (SIGABRT, rc=-6, "std::array ... operator[] ... __n < this->size()") when handed an *illegal* position - found while prototyping, by feeding it a hand-written FEN with nine white pawns. Legal FENs are fine. `top_moves` returns `[]` rather than raising when the process dies mid-search, and `Hint` spawns a fresh process per request instead of reusing one, precisely so a dead engine can't poison every later hint.
- `src/analysis.cr` - `Analysis` runs Stockfish over every position of a game and turns evaluation swings into standard PGN annotations: a NAG (`$2` mistake, `$4` blunder, `$6` inaccuracy - thresholds `MISTAKE_THRESHOLD`/`BLUNDER_THRESHOLD`/`INACCURACY_THRESHOLD`, in centipawns) plus a `{[%eval X] Label. Better: <SAN>.}` comment, embedded in the PGN itself rather than a separate database - so the analysis is portable to any other PGN-reading tool, and detecting "already analyzed" is just `pgn.includes?("[%eval")`. `.analyze` evaluates N+1 positions for an N-move game (the position *before* each move doubles as the position *after* the previous one, so each position is only evaluated once), computing a "better move" suggestion from the *pre*-move position's best line (via `Board#move_to_san`, which - unlike the SAN built into a played move - has no way to know if it would deliver check/mate without simulating it, so it never gets a `+`/`#` suffix) and appending the real check/mate suffix to the *played* move's SAN afterward, from the actual resulting position. Mate scores don't compare numerically to centipawn scores, so `pseudo_cp` maps them onto the same scale (sooner mates more extreme in either direction) before computing the swing. `.parse` and `.embed` are the read/write sides of the same format - `.parse`'s regex tokenizer (`TOKEN_RE`) handles an optional move number, the SAN token, an optional NAG, and an optional `{...}` comment (which itself may contain spaces/punctuation) per move, and works identically whether or not the PGN has any annotations at all. A flagged move's comment can carry a second, later-added tag, `[%explain ...]` (`EXPLAIN_RE`/`.with_explanation`/`Note#explanation`) - the AI's on-demand prose explanation of *why* (see `Replay#explain`), sanitized of `[]{}` characters before embedding since those would break the comment's own syntax. `.better_san` pulls the suggested move back out of a flagged note's own rendered "Better: X." text rather than keeping it as a separate stored field - one less thing for `.embed`/`.parse` to round-trip.
- `src/hint.cr` - `Hint` is the one place that asks Stockfish for a ranked shortlist, shared by the human's typed `hint` command (`Chess#show_hint`) and the model's `hint` tool (`AI#hint_response`) - both need the same engine call and the same information, only rendered for a different reader. `MOVES = 5` is hardcoded on purpose (wide enough that a hint is visibly a *choice* rather than one dictated move, narrow enough that ranking all of them stays fast - ~1.3s at depth 16 here); `DEPTH` reads `CHESS_HINT_DEPTH` (default 16) since search depth, not list length, is the knob worth tuning. `.suggestions(board, white)` returns `Array(Suggestion)?` with three deliberately different outcomes: a non-empty list, `[]` meaning that side genuinely has no legal move (checkmate/stalemate - a real answer, returned before any engine is spawned so it's testable without Stockfish), and `nil` meaning no usable engine (not installed, process died, or nothing in its output matched a legal move). It **never raises** - a hint is a convenience, and losing a live game to one that failed is not acceptable - with failures going to `GameLog.error`. It spawns a *fresh* short-lived `Stockfish` per call and `close`s it in `ensure`, unlike `Analysis` which reuses one process for a whole game: this build aborts on an illegal position (see `src/stockfish.cr`), so a long-lived shared engine could be poisoned by one bad FEN and stay broken for every later hint, whereas a dead process here costs one failed hint. Two normalization details matter for correctness: `normalize_move` clips a UCI move to its first 4 chars, because the engine spells a promotion `a7b8q` while `Board#legal_moves` spells the same move `a7a8`, so matching without clipping would silently discard *every* promotion suggestion - the exact moment a hint is most useful; and `.build` drops a lane whose first move is already in the list, because MultiPV can rank two different promotion pieces to one square (`a7b8q`, `a7b8n`) as separate lanes, which this app - always promoting to queen - has to show as one move rather than two identical rows. Scores are rendered from the side to move's perspective and left unqualified (cp as `+0.34`, mate as `mate in 1`/`get mated in 2`), because saying "White is better" would be wrong half the time. `render_for_human` leads with SAN (what a player reads); `render_for_ai` leads with long algebraic (the exact string the model must pass to its own `move` tool - making it translate SAN back is a needless chance to get it wrong) and ends with an explicit "suggestions only - you may play any legal move" note, without which a model reading a ranked list tends to treat #1 as an instruction.
- `src/context.cr` - `Context` trims the message list before it's sent. `AI`'s `@messages` is append-only and grows for the whole game, but in chess nothing past the position needs the transcript: an untrimmed log ends up holding a dozen FENs and a dozen engine rankings describing positions that no longer exist, each phrased as though it were current - which is a real correctness problem late in a game, not just a token cost. `.units` groups the log into indivisible exchanges so a tool response is never separated from the assistant message that requested it (some providers reject the whole request with a 400 otherwise, which would lose the game - `spec/context_spec.cr` asserts this invariant across many trim depths); `.trim` keeps the first unit (the system prompt, which is what states who the model is and which color it plays), an optional summary standing in for everything elided, and the last `RECENT_EXCHANGES` units; `.eliding?` tells callers whether anything would actually be dropped, so a short game is sent untouched rather than getting a summary invented for history that was never removed.
- `src/ai.cr` - `AI` wraps an OpenAI-compatible chat completions API (defaults to local Ollama). `initialize`'s `@ai_white` (default `false`, i.e. the AI plays black unless told otherwise) is set once from `Chess.new`'s `!@human_white` and read everywhere the AI needs to know its own color - the system prompt's "the human is X and you are Y" wording, `next_move`/`next_move_loop`'s `legal_moves`/`in_check?`/`to_fen` calls, and the `resign` tool's result message/PGN code, all keyed off it instead of a hardcoded `false`. The `resign` tool call itself is gated on `board.only_pawns_left?(@ai_white)` (see `src/board.cr`) before it's ever allowed to raise `GameOver` - a rejected call gets a normal tool response telling it to keep playing instead, same retry-within-the-turn pattern `setup_position`/`play_for_human` use for their own validation. This replaced a prompt-only version of the rule (a material deficit of "a full rook or more") after a model (DeepSeek) resigned a second time with a bishop and six pawns still on the board, no check, 20+ legal moves, and no mate in sight (confirmed by feeding the final position to Stockfish) - right at the edge of that threshold, proving prompt wording alone isn't a reliable enough backstop for this. The system prompt and the tool's own description still spell out the same bar in words (nothing left but pawns and king, and even then only for a real forced mate or a truly hopeless pawn ending) so the model isn't surprised by the rejection, but the actual gate is the board fact, not the wording. `chat_loop`'s `board` tool uses `!@ai_white` instead, since chat always happens during the human's turn, not the AI's. `next_move` also has to handle the AI playing white and moving first, when `board.moves` is still empty - `board.moves.last` on an empty array is an `IndexError`, so that case gets a distinct "you move first" opening prompt instead of "I played #{board.moves.last}". `initialize`'s optional `resume_moves` briefs a freshly-constructed `AI` with a saved game's move list as its first message, for `Chess.new(saved)` - it's the best available substitute for the real prior conversation, which is in-memory only and doesn't survive a restart. Otherwise maintains the full message history (`@messages`) for the game session (including tool call/response messages) so the model has context across turns - `next_move` and `chat` both read/append to it; only `resolve_move(board, text, white)` is a separate, stateless one-off request (its own tools, its own throwaway message list, and its own `white` param since it resolves the *human's* move and the human may be either color) - since it's a focused notation-resolution task, not part of the game conversation. `next_move`/`chat` both push their one "new" message once in a public method (`next_move`/`chat`) and then recurse through a private `_loop` method (`next_move_loop`/`chat_loop`) that does *not* re-push it - calling `next_move` (not the loop) from inside the loop was a bug that duplicated the "I played X, your turn" message on every tool call or plain-text non-answer from the model. `next_move` also derives per-turn notices in `AI#turn_notices` - being in check (the model can't reliably work this out from FEN alone), having exactly one legal move (often a non-obvious tactic like blocking a check, and listing it alongside N dead-end options wasn't enough for the model to find it reliably), the previous attempt's rejection reason, and the Stockfish ranking - and these are deliberately *transient*: they're appended to that one request by `request_messages` and never pushed into `@messages`, because they describe a single position and persisting them is precisely how the transcript accumulates a dozen contradictory claims about what's "current". The same applies to `chat`'s "that wasn't a move" reminder. `request_messages` is therefore the only path from `@messages` to the wire, and it trims via `Context` (see above), substituting `context_summary` - move list plus the real current FEN - for whatever was elided. That summary's side-to-move is derived from `board.moves.size.even?` rather than hardcoded to `@ai_white`, since the same summary serves chat (the human's turn) and a `setup_position`/`undo` handoff where the next move may belong to either side. The `hint` tool is offered in `chat_loop` only (answering "what should I play?" for the human); there's no point offering it in `next_move_loop`, where its answer is already attached to every request. `next_move_loop` exposes `moves`/`board`/`move`/`resign` (calling `resign` raises `GameOver` directly from within `AI`, same as `Board`'s check/checkmate/stalemate/draw detection does from `Chess` - it propagates out through `next_move` uncaught); a tool call matching none of those (e.g. a model calling `undo`/`setup_position` out of context - they're only ever offered in `chat_loop`, but still appear by name in the shared `@messages` history from earlier chat turns, which has been observed to confuse a model into calling them again mid-`next_move`) gets a tool response saying so instead of crashing, same as a `move` call with a missing/malformed `nextMove` argument - both used to fall through to a catch-all that assumed `tool["function"]["arguments"]["nextMove"]` always existed, raising an uncaught `KeyError` ("Missing hash key") that propagated all the way past `Chess#run`'s rescues to the top-level menu, losing the game's progress-since-last-save; `chat_loop` exposes `moves`/`board`/`undo`/`setup_position`/`play_for_human`/`hint` (chat can look but not touch game state via the AI's own `move` tool, which `next_move_loop` alone exposes, though it can retract a move via `undo`, jump to an arbitrary position via `setup_position`, play the human's own current move via `play_for_human`, or consult the engine via `hint`) - calling `undo` similarly raises an `UndoRequested` (count from the tool's `count` arg, defaulting to 1) straight out of `chat`, uncaught by `AI` itself, for `Chess#next_turn` to catch; its description explicitly tells the model to only call it when the human clearly asks, never on its own initiative. `setup_position` (e.g. "show me the Ruy Lopez") takes a `moves` array the model is expected to translate into correct long algebraic notation itself from whatever the human described, and is validated with `invalid_setup_reason` - replaying the sequence on a throwaway `Board.new` (never the live `board` `chat` was given) before committing to anything - which returns the first illegal move and why, or `nil` if the whole sequence is legal; only a `nil` (valid) result raises a `SetupRequested`, same shape as `undo`'s exception, while an invalid one gets pushed back as a normal tool response (the rejection reason) so the model can correct itself and retry within the same chat turn rather than the human ending up looking at a wrong position. Its description likewise tells the model to only call it on a clear request, never its own initiative - unlike `undo`, where a bad call is harmless either way, a wrong `setup_position` call would otherwise silently replace the real game with the wrong position if it weren't validated first. `play_for_human` (e.g. "move for me") takes a single `nextMove` the model is expected to choose itself, validated against `board.legal_moves(!@ai_white)` (the *human's* color, not the AI's own) before raising a `MoveRequested` - an unparseable or illegal candidate gets pushed back as a normal tool response (listing the human's actual legal moves) instead, same retry-within-the-turn pattern as `setup_position`'s validation; its description likewise says to only call it on a clear request, never speculatively. `chat_loop`'s own catch-all is similarly an explicit `when "board"` now rather than treating any unrecognized name as `board` by default (a model calling `move`/`resign` - only ever offered in `next_move_loop` - out of context would otherwise have silently gotten back a FEN under the wrong tool name). Both loops iterate *every* tool call in the assistant's message and push a matching tool response for each `tool_call_id`, not just the last one - a model can return more than one tool call in a single response (seen in practice from DeepSeek), and some providers strictly enforce that every `tool_call_id` an assistant message carries gets answered before `@messages` is sent again, rejecting the whole request with a 400 otherwise; answering only the last one left earlier ones dangling and broke the very next request. Whatever the model's `move` tool call requests is exactly what gets printed and played - see `next_move`'s `weak_move_chance` roll above for how skill level is simulated instead. `resolve_move` gives the model the FEN and the exact list of white's legal moves and asks it to pick one via `propose_move`, or call `not_a_move` if the instruction isn't a resolvable move; `Chess#next_turn` calls `record_move_resolution` after a successful resolution to fold that exchange into `@messages`. `explain_move` is a third stateless one-off (no tools, plain chat completion) - given a FEN, the move actually played, and Stockfish's own principal variation for both that move and its suggested alternative, it narrates *why* the played move was worse; deliberately asked to explain given evidence rather than to find or judge anything itself, since the model's own chess play elsewhere in this app has repeatedly shown it isn't reliable at the latter. Retries failed (non-2xx) HTTP responses up to 3 times, but a genuine `IO::TimeoutError` (the request took longer than `TIMEOUT`, an instance `HTTP::Client`'s `read_timeout`/`connect_timeout`, set once in `initialize`) is never retried - retrying with the same time budget just multiplies the wait - it's caught once and re-raised as a clear message naming the model and how to configure `CHESS_TIMEOUT`. The system prompt also tells the model its own time budget, so it isn't just externally cut off - though local-model adherence to that kind of instruction is inherently best-effort. A non-2xx response is retried up to 3 times, as is any `IO::Error` from a dropped connection (`IO::EOFError`'s "Unexpected end of http response", or a plain "Connection reset by peer" - both seen from real providers' proxies silently killing a kept-alive connection) - which also closes `@client` first, since retrying on the same dead socket would just hit the identical error again; `IO::TimeoutError` is a subclass of `IO::Error` but is re-raised rather than retried here (see below), since it's the one failure that's never worth retrying. Exhausting all 3 attempts raises with the last failure's actual detail (HTTP status + body, or the connection error), so e.g. a bad API key or wrong model name on a non-Ollama provider is diagnosable instead of a bare "failed" message. `post_chat_completion` runs the actual HTTP call on a spawned fiber via `with_spinner`, while the calling fiber polls a `Channel` with `select`/`timeout` to animate a Braille spinner plus an elapsed-seconds counter - otherwise a slow response and a hung one look identical (nothing printed at all) until one of them eventually returns. The spawned block's exceptions (including the timeout) are caught and sent through the channel as a value, then re-raised on the receiving side - Crystal doesn't propagate an unhandled exception in a spawned fiber back to whatever's waiting on it, so without that, any exception in the HTTP call (not just a timeout - a plain connection refused would do it too) left the spinner looping forever on a channel that was never going to receive anything.

## Conventions

- Board coordinates are zero-indexed internally (`x`: 0-7 for files a-h, `y`: 0-7 for ranks 1-8); `pieces` is indexed `[y][x]`.
- Moves are long algebraic notation, optionally with `x` for captures (e.g. `e2e4`, `g1xf3`), matched by `/^\D\d(x)?\D\d$/`.
- `white` is `Bool?` on `ChessMan` (nilable so `Empty` squares can be distinguished from either color).
- 2-space indentation, per `.editorconfig`.
