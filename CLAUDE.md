# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A terminal chess app written in Crystal. The human plays white; black is played by a local Ollama model (`qwen3.8:latest`, currently) via its OpenAI-compatible chat completions endpoint, using function/tool calling. White can enter moves in long algebraic notation (e.g. `e2e4`) or as natural language (e.g. "move my king pawn up two squares"), which the model resolves against the actual legal moves. The board is rendered with unicode chess characters and ANSI background colors.

## Commands

- Build: `shards build` (produces `./bin/chess`)
- Run: `./bin/chess`, or `crystal run src/chess.cr` during development
- Run all specs: `crystal spec`
- Run a single spec file: `crystal spec spec/pieces/pawn_spec.cr`
- Run a single example: `crystal spec spec/pieces/pawn_spec.cr -e "allows white pawn to move forward one square"`

Requires a local Ollama server by default, with a tool-calling-capable model pulled (`qwen3.8:latest`, currently). The endpoint, model, and per-request timeout are configurable via `OPENAI_BASE_URL`/`OPENAI_MODEL`/`OPENAI_TIMEOUT` env vars (see `src/ai.cr`'s `BASE_URL`/`MODEL`/`TIMEOUT` constants - `TIMEOUT` defaults to 300s), so pointing them at the real OpenAI API (and setting `OPENAI_API_KEY`) works too.

Post-game analysis (`Analysis`, below) needs a `stockfish` binary on `PATH` - optional, degrades to a one-line warning when absent, and one spec (`spec/analysis_spec.cr`, tagged `"stockfish"`) calls the real engine and self-skips via `pending!` when it's missing.

## Architecture

- `drain_stdin` (top-level function in `src/chess.cr`, not a `Chess` method - callable from both the module-level menu loop and inside `Chess`) - sets `STDIN.read_timeout` to 50ms and reads until it times out or hits EOF, discarding whatever it reads, then resets `read_timeout` back to `nil` (leaving it set would give *every* later blocking `gets` call the same 50ms timeout and raise `IO::TimeoutError` on real, valid waits). Called right before every prompt-reading `gets` (skill-level selection, white's move, the main menu, the overwrite-confirmation). Fixes a real bug: without it, a stray keystroke typed while the AI was "thinking" sits in the OS input buffer and gets consumed by whichever `gets` call happens next - not the prompt that was on screen when it was typed - so e.g. quitting at the post-game menu could silently turn into "start a new game" because an earlier keypress was still queued up.
- `src/chess.cr` - entry point. The top-level loop is a menu (new game / resume game / browse saved games / quit) dispatching to `Chess.new.run`, `Chess.new(SavedGame.load).run`, or `Replay.browse`; choosing "new game" while a `SavedGame` exists asks for confirmation before it gets overwritten. `Chess` is the game loop itself. Loads the human's `Profile` and, when resuming, replays the saved moves onto a fresh `Board` and re-briefs a fresh `AI` with the game-so-far via `resume_moves` - the model's exact prior conversation can't survive a restart, only the position and move list. Not resuming, it prompts for a `SkillLevel` at startup instead. Typing `quit`/`exit`/`save` on white's turn (or stdin EOF) just raises a plain message ending `run` - no special handling needed to avoid losing progress, because `save_progress` (below) already persists after every move. Typing `resign` (white) or the model calling the `resign` tool (black, see `src/ai.cr`) instead raises a `GameOver` - a real result, not just a pause, so it flows through `finish_game` the same as checkmate/stalemate/draws. Alternates turns between white (stdin input) and black (`AI#next_move`). White's `gets` returning `nil` (stdin EOF) raises immediately rather than looping - `gets` never blocks again once stdin is closed, so treating it as "no more input" is what stops that from becoming a busy loop; blank input is silently ignored (re-prompts) without spending an AI call on it. White's non-notation input is first sent to `AI#resolve_move`, which tries to resolve it to one of the position's actual legal moves; on success the exchange is recorded into the AI's shared history via `AI#record_move_resolution` (so later chat/moves have it in context, not just the bare notation `board.moves` shows) and the move is played; if that fails (not a move, ambiguous, illegal), it falls back to `AI#chat` so the human can "talk" to the AI mid-game. A failed `board.turn` sets `@last_error` to `"invalid move: X - #{board.explain_invalid_move(move, white)}. try again!"` - a concrete reason (off the board, not your piece, square occupied by your own piece, that piece can't move that way, or leaves your own king in check), not just a bare rejection - threaded into the *next* `AI#next_move` call so the model actually sees why its last attempt failed (this is a plain instance var precisely so it survives across `next_turn` calls for the same side's turn, unlike a method-local variable). ...`Chess#save_progress` writes the move list out to `SavedGame` (`~/.chess/in_progress.json`) after *every* successful move, not just on a clean exit. After every successful `Board#turn`, `Chess#report_game_status` checks the side to move next for checkmate/stalemate, the fifty-move rule, or threefold repetition - each raises a `GameOver` (carrying a PGN result code, e.g. `"1-0"`) caught by `run`'s typed `rescue ex : GameOver`, which calls `Chess#finish_game` to clear the now-obsolete `SavedGame`, update and save the `Profile`'s Elo rating (`record_result`, against the AI's `SkillLevel#elo_midpoint` as the opponent rating), and write the game out via `Board#to_pgn`. A plain invalid-move abort (`error_count > 3`) raises an untyped exception instead, falling through to the generic `rescue ex` so it does *not* touch the profile, write a PGN, or clear the in-progress save. Check (not mate) just prints a warning.
- `src/board.cr` - `Board` holds the 8x8 `pieces` grid (`Array(Array(ChessMan))`, indexed `[y][x]`), captured-piece lists, the long-algebraic move history (`moves`, formatted like `"w: e2e4"`), and the SAN move list (`sans`, e.g. `"Qxh4#"`) built for PGN export. `Board#turn` is the single chokepoint for all move legality and side effects: notation parsing, bounds/ownership checks, delegating to the piece's `valid?`, rejecting moves that leave the mover's own king in check (`move_leaves_king_in_check?`, via a simulate-then-revert on the piece grid), computing the move's SAN prefix (`san_prefix_for`, which must run before the board mutates - it needs the pre-move piece identity, capture, and disambiguation), then applying castling, pawn promotion (auto-queen), en passant setup/capture (flags expire after the single following move - the capture side of this is only applied when the mover was a pawn *and* the destination square was empty before the move, i.e. `was_pawn_move && lost.is_a?(Empty)`; without that guard, an ordinary diagonal pawn capture onto an occupied square would additionally, wrongly, delete whatever piece happened to sit on the "captured en passant" square, since the rank/file arithmetic alone can't tell a real en passant from a normal capture), updating captured lists, the fifty-move clock, position-repetition count, and finally the SAN's check/mate suffix (needs the post-move position, so it's the last thing computed). `Board#legal_moves(white)` enumerates every fully-legal destination for a color (reused for check/checkmate/stalemate detection, skill-level blunder injection, SAN disambiguation, and grounding the natural-language move resolver). `Board#to_fen(white_to_move)` renders the position as FEN for the AI's `board` tool, built on the same `position_key` (piece placement + side to move + castling rights + en passant target, without the move counters) used to detect `draw_by_repetition?` in `position_counts`; `draw_by_fifty_move_rule?` just checks `halfmove_clock >= 100`. `Board#to_pgn(headers, result)` renders `sans` as a standard PGN move list with header tags, ending in a blank line (not just a newline) per the PGN spec's game separator - each of our saved games is its own file, but external multi-game database tools (e.g. PyChess) build their game list from `[Event]` tags and need that blank line to also find where each game's movetext ends, or they'll list a game but show it blank when opened; `Board#find_move_for_san(san, white)` is the inverse - given a SAN token, finds which of `legal_moves` produces it, used by `Replay` to step through a saved game. `Board#move_to_san(move, white)` is a third variant, for a candidate move that was never actually played (e.g. an engine's suggestion in `Analysis`) - it can't include a check/mate suffix, since that needs the position after playing the move. `Board#explain_invalid_move(move, white)` retraces `#turn`'s own checks in the same order and returns which one a rejected move actually failed - only meaningful to call after `#turn` already returned `false`. `Board#draw` prints the board with hardcoded ANSI codes per rank (not to be confused with the draw-detection methods above).
- `src/pieces/` - one class per piece type, all subclassing `ChessMan` (`src/pieces/chessman.cr`), which is abstract and declares `valid?(board, from_x, from_y, to_x, to_y)`. Each piece's `valid?` computes candidate destination `Spot`s given the current board state and checks membership; pieces do not mutate board state themselves and don't consider check/pins - that's `Board`'s job. `Empty` is a null-object placeholder for empty squares, also a `ChessMan`.
- `src/spot.cr` - simple `Comparable` `(x, y)` coordinate value type used when generating candidate moves.
- `src/skill_level.cr` - `SkillLevel` enum (Novice through Grandmaster) with an Elo range and a `weak_move_chance` per tier. `AI#next_move` rolls against it each turn and, if it hits, adds a system message explicitly telling the model to play like that tier *before* it chooses - the model's own account of the game always matches the move it actually submits; there is no post-hoc substitution (an earlier version silently swapped in a random legal move after the model chose, which desynced the model's belief about the position from the real board - it would report having played one move while a different one appeared on the board). Master/Grandmaster never get the nudge - their real strength is whatever the underlying model can play. `elo_midpoint` gives a representative Elo per tier, used as the "opponent rating" for the human's Elo update.
- `src/profile.cr` - `Profile` is the human player's persistent record (name, `rating`, win/loss/draw counts), serialized via `JSON::Serializable` to `~/.chess/profile.json` (`Profile.load`/`#save`). `#record_result(opponent_rating, score)` applies the standard Elo formula (K=32).
- `src/game_over.cr` - `GameOver < Exception` carries a PGN result code (`"1-0"`/`"0-1"`/`"1/2-1/2"`) alongside its message, so `Chess#run` can tell a real chess ending apart from any other exception.
- `src/saved_game.cr` - `SavedGame` is the one in-progress-game slot (only one at a time), serialized to `~/.chess/in_progress.json`: the plain-notation move list, the chosen `SkillLevel` (by name), and a timestamp. `Chess` writes it after every move and clears it when a game actually ends, so it only ever exists while a game is genuinely mid-play.
- `src/replay.cr` - `Replay` (a module of class methods, no state of its own) lists PGN files under `~/.chess/games`, parses each one's header tags and move list via `Analysis.parse` (which returns SAN plus any embedded NAG/comment, working equally on plain and already-analyzed PGN), and resolves the SAN tokens back to long-algebraic moves one at a time via `Board#find_move_for_san(san, white)` - which just searches `legal_moves` for the candidate whose `san_prefix_for` output matches, avoiding a separate SAN parser. If the game isn't yet annotated (`Analysis.annotated?`) and Stockfish is available, `#maybe_analyze` offers to run it (`Analysis.analyze`, showing progress) and rewrites the file in place via `Analysis.embed` so this only ever runs once per game; if Stockfish isn't installed, it prints a one-line warning and replay continues unannotated. `#step` then lets the user move through the resolved move list (`n`/`p`/`j <n>`/`q`), rebuilding a fresh `Board` from `setup` up to the current index on every step rather than supporting true undo, printing the current move's eval (always, once analyzed) and its label/better-move (when flagged) above the board, plus the long-algebraic move played next to the `move N/M` counter - the board itself stays exactly where it was, unaffected. On a flagged move, an `[e]xplain` option appears; `#explain` shows the cached `Note#explanation` if one exists, or computes one by pairing a fresh single-position `Stockfish` lookup (for the principal variation on both sides - the concrete "what actually happens" evidence) with `AI#explain_move` (which only narrates that evidence, never calculates anything itself - seconds-long lookups are fine here since it's one on-demand call, not a whole game), then persists it back into the same file via `Analysis.with_explanation` + `Analysis.embed` so it's never recomputed. `#explain` is called from a `begin/rescue` in `#step`, not left to propagate - an `AI#explain_move` timeout (or any other error) would otherwise climb all the way past `Replay`/`Chess` to the top-level menu `loop`, which has no rescue of its own and would crash the whole program instead of just failing this one lookup.
- `src/stockfish.cr` - `Stockfish` is a thin UCI (Universal Chess Interface) client for a local `stockfish` subprocess, used only by `Analysis`, never during live play. `.available?` checks `Process.find_executable("stockfish")` rather than assuming; `#evaluate(fen)` sends `position fen ...` + `go depth N` over the process's stdin and parses `info ... score cp|mate N ... pv ...` / `bestmove` lines off stdout, returning the side-to-move's score, suggested move, and principal variation (the forced-ish continuation, in long algebraic notation - kept for `Replay#explain` to hand the AI as concrete evidence, not asked of it). One process is kept open and reused across the whole game's positions during `Analysis.analyze`, not respawned per move; `Replay#explain` spins up a separate short-lived one for its own one-off before/after lookup.
- `src/analysis.cr` - `Analysis` runs Stockfish over every position of a game and turns evaluation swings into standard PGN annotations: a NAG (`$2` mistake, `$4` blunder, `$6` inaccuracy - thresholds `MISTAKE_THRESHOLD`/`BLUNDER_THRESHOLD`/`INACCURACY_THRESHOLD`, in centipawns) plus a `{[%eval X] Label. Better: <SAN>.}` comment, embedded in the PGN itself rather than a separate database - so the analysis is portable to any other PGN-reading tool, and detecting "already analyzed" is just `pgn.includes?("[%eval")`. `.analyze` evaluates N+1 positions for an N-move game (the position *before* each move doubles as the position *after* the previous one, so each position is only evaluated once), computing a "better move" suggestion from the *pre*-move position's best line (via `Board#move_to_san`, which - unlike the SAN built into a played move - has no way to know if it would deliver check/mate without simulating it, so it never gets a `+`/`#` suffix) and appending the real check/mate suffix to the *played* move's SAN afterward, from the actual resulting position. Mate scores don't compare numerically to centipawn scores, so `pseudo_cp` maps them onto the same scale (sooner mates more extreme in either direction) before computing the swing. `.parse` and `.embed` are the read/write sides of the same format - `.parse`'s regex tokenizer (`TOKEN_RE`) handles an optional move number, the SAN token, an optional NAG, and an optional `{...}` comment (which itself may contain spaces/punctuation) per move, and works identically whether or not the PGN has any annotations at all. A flagged move's comment can carry a second, later-added tag, `[%explain ...]` (`EXPLAIN_RE`/`.with_explanation`/`Note#explanation`) - the AI's on-demand prose explanation of *why* (see `Replay#explain`), sanitized of `[]{}` characters before embedding since those would break the comment's own syntax. `.better_san` pulls the suggested move back out of a flagged note's own rendered "Better: X." text rather than keeping it as a separate stored field - one less thing for `.embed`/`.parse` to round-trip.
- `src/ai.cr` - `AI` wraps an OpenAI-compatible chat completions API (defaults to local Ollama). `initialize`'s optional `resume_moves` briefs a freshly-constructed `AI` with a saved game's move list as its first message, for `Chess.new(saved)` - it's the best available substitute for the real prior conversation, which is in-memory only and doesn't survive a restart. Otherwise maintains the full message history (`@messages`) for the game session (including tool call/response messages) so the model has context across turns - `next_move` and `chat` both read/append to it; only `resolve_move` is a separate, stateless one-off request (its own tools, its own throwaway message list), since it's a focused notation-resolution task, not part of the game conversation. `next_move`/`chat` both push their one "new" message once in a public method (`next_move`/`chat`) and then recurse through a private `_loop` method (`next_move_loop`/`chat_loop`) that does *not* re-push it - calling `next_move` (not the loop) from inside the loop was a bug that duplicated the "I played X, your turn" message on every tool call or plain-text non-answer from the model. `next_move` also checks `board.in_check?(false)` (adds an explicit "you are in check" notice - the model can't reliably derive this from FEN alone) and `board.legal_moves(false).size == 1` (adds "you have exactly one legal move: X" when forced - a single-legal-move position is often a non-obvious tactic like blocking a check, and listing it alongside N other dead-end options wasn't enough for the model to find it reliably). `next_move_loop` exposes `moves`/`board`/`move`/`resign` (calling `resign` raises `GameOver` directly from within `AI`, same as `Board`'s check/checkmate/stalemate/draw detection does from `Chess` - it propagates out through `next_move` uncaught); `chat_loop` exposes just `moves`/`board` (chat can look but not touch game state). Whatever the model's `move` tool call requests is exactly what gets printed and played - see `next_move`'s `weak_move_chance` roll above for how skill level is simulated instead. `resolve_move` gives the model the FEN and the exact list of white's legal moves and asks it to pick one via `propose_move`, or call `not_a_move` if the instruction isn't a resolvable move; `Chess#next_turn` calls `record_move_resolution` after a successful resolution to fold that exchange into `@messages`. `explain_move` is a third stateless one-off (no tools, plain chat completion) - given a FEN, the move actually played, and Stockfish's own principal variation for both that move and its suggested alternative, it narrates *why* the played move was worse; deliberately asked to explain given evidence rather than to find or judge anything itself, since the model's own chess play elsewhere in this app has repeatedly shown it isn't reliable at the latter. Retries failed (non-2xx) HTTP responses up to 3 times, but a genuine `IO::TimeoutError` (the request took longer than `TIMEOUT`, an instance `HTTP::Client`'s `read_timeout`/`connect_timeout`, set once in `initialize`) is never retried - retrying with the same time budget just multiplies the wait - it's caught once and re-raised as a clear message naming the model and how to configure `OPENAI_TIMEOUT`. The system prompt also tells the model its own time budget, so it isn't just externally cut off - though local-model adherence to that kind of instruction is inherently best-effort. `post_to_openai` runs the actual HTTP call on a spawned fiber via `with_spinner`, while the calling fiber polls a `Channel` with `select`/`timeout` to animate a Braille spinner plus an elapsed-seconds counter - otherwise a slow response and a hung one look identical (nothing printed at all) until one of them eventually returns. The spawned block's exceptions (including the timeout) are caught and sent through the channel as a value, then re-raised on the receiving side - Crystal doesn't propagate an unhandled exception in a spawned fiber back to whatever's waiting on it, so without that, any exception in the HTTP call (not just a timeout - a plain connection refused would do it too) left the spinner looping forever on a channel that was never going to receive anything.

## Conventions

- Board coordinates are zero-indexed internally (`x`: 0-7 for files a-h, `y`: 0-7 for ranks 1-8); `pieces` is indexed `[y][x]`.
- Moves are long algebraic notation, optionally with `x` for captures (e.g. `e2e4`, `g1xf3`), matched by `/^\D\d(x)?\D\d$/`.
- `white` is `Bool?` on `ChessMan` (nilable so `Empty` squares can be distinguished from either color).
- 2-space indentation, per `.editorconfig`.
